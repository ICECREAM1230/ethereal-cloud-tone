## 结论

## 发现：未武装状态被显示成光照

- 位置：`components/b_control/b_engine.c` 的 `b_engine_snapshot()` 将 `shade` 设为 `active_beams`；`host/b_board_debugger/gui.py` 的 `_refresh_state()` 把 `shade=0` 显示成“光照”。
- `active_beams` 实际表示已经武装、正在测量遮光时长的通道，不能代表全部物理遮光状态。
- 定向探针复现：原始输入 `0xFFF`、滤波后遮光 `0xFFF`，但尚未武装，故 `status.shade=0`，界面显示“光照”。这是状态语义问题，不应据此判断传感器已受光或没有信号。
- 建议：区分受光、遮光、等待首次受光/未武装，并把物理输入状态与计时状态分别表示。本轮只记录问题，未修改协议或界面。

## 当前弹奏规则

| 阶段 | 输入与行为 |
| --- | --- |
| 首次准备 | 必须先得到至少一次稳定受光低电平；上电持续高电平不触发旧遮挡 |
| 遮挡 | 输入变高并稳定2ms后开始记录，遮挡期间不发送Note On |
| 恢复受光 | 输入恢复低电平并稳定2ms，按合格原始边沿间的遮光时长计算力度并发送Note On |
| 自动关音 | 默认在Note On后200ms发送Note Off；遮挡更久不会延长这个gate |
| 力度 | 默认20..500ms对应16..127；更短/更长的合格脉冲在端点限幅，100ms对应35；允许在既有配置中反向曲线 |

因此当前规则是恢复光束后发声。持续遮住不响、上电一直高电平时第一次恢复只完成武装，均是现有规则。不能把软件试奏通过当作物理遮光通过。

另一个集成注意点：当前 `route=auto`，USB连电脑时优先只向USB发送，即使BLE也可用也不会同时发送。无线演奏需使用已有的BLE路由或相应连接方式，本轮未修改路由。
